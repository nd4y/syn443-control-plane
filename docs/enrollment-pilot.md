# M2 identity and device-enrollment pilot

This is an isolated vertical implementation, not the complete M2 milestone or full administration panel. The Android protocol core is tested on JVM; browser UI, Keystore persistence, device enrollment integration, invitations and physical login acceptance are still pending. M1 cellular/Doze/energy gates remain separate.

## Authority and data flow

The native client uses an external browser, authorization code, S256 PKCE, exact `syn443://oauth/callback`, state, nonce and issuer checks. The protocol core verifies real RSA signatures, audience, authorized party, expiry and key-bound access claims. A nonexportable Android Keystore adapter and a durable single-owner login coordinator are the next integration step. No password form or client secret belongs in the APK.

The test-realm Android public client requires DPoP and includes the custom `syn443-api` access-token audience. Code and refresh credentials bind to the same P-256 key. The web fixture client remains a separate loopback OAuth conformance client. Neither realm role grants Keycloak administration or configuration access.

`POST /v1/devices/enroll` requires the pinned Keycloak issuer, RS256 signature, API audience, Android authorized party, expiry, cnf.jkt and a fresh ES256 DPoP proof by that key. An owner-authored assignment and active-device limit are checked separately in PostgreSQL. Unknown users receive no common/example configuration. A server challenge nonce precedes enrollment. The registration body carries a random idempotency ID, public key and supported capabilities; POST proofs bind the exact raw body bytes using `req_hash` (SHA256/base64url extension). Do not normalize the body between retries.

The response is a separate opaque device session: access at most ten minutes, absolute refresh family at most one day, both capped by the assignment. Tokens bind to the key; device ID is not a credential. Nonces, proof replay records, refresh hashes, idempotent replies and a monotonic maximum server-time fence survive API-process recreation. Refresh rotates both tokens and nonce. A fresh proof retry with the same request ID/body can recover a lost response for three minutes; a different request using an old refresh token revokes its family. Revoke uses its own durable receipt, so a matching fresh-proof retry can confirm an already completed action. Account/device expiry or revocation blocks further access. Offline client leases expire independently; upstream proxy/overlay revocation is not implemented here.

## Separate publication authority

`enrollment-api` loads no signing key and performs no DDL/assignment writes. An owner migration/authorization CLI and a separate `enrollment-worker` handle these tasks. A grant file supplies the exact issuer/subject, active-device limit, expiration (at most seven days) and policy template. The API sees its hash. The worker independently verifies the initial encrypted OIDC/DPoP receipt, including key and raw-body binding, against that immutable grant. It never accepts an API-submitted signing request or arbitrary template. Later renewals require an approved immutable identity, matching current grant hash and enabled account/device.

Only the publisher role can approve or update signed publications. Its transaction rechecks account, device, public-key thumbprint, source-body hash and revision before committing. Conflicting/stale work cannot overwrite a newer revision. Failed renewal preserves the preceding authorized publication and records a bounded retry. The worker polls durable desired state; it is not the planned general-purpose job/cohort system. Policy leases are at most one hour and never exceed the grant. Clients must verify the device-scoped ES256/JCS bundle using previously trusted roots and the existing transactional policy coordinator.

## Private pilot operation

The server binaries bind the API listener to an explicit loopback IP. HTTPS is required; plain HTTP is limited to explicit synthetic loopback fixtures. Remote PostgreSQL requires verified TLS, including every fallback. Use separate service identities, owner-only regular configuration/grant/signing files and a protected parent directory. The API and publisher share a purpose-bound AEAD encryption key for stored receipts/replies/publications; opaque tokens are hashed. Never log or upload these files, tokens, grants, real device IDs or phone evidence.

Create an empty, separately owned database. The owner runs `enrollment-admin migrate`; it must not be an application database owned by another project. Create independent NOINHERIT, NOBYPASSRLS LOGIN roles named `syn443_identity_api` and `syn443_identity_publisher`, with no privileged flags or role memberships. Manage passwords outside source. Run `enrollment-admin roles` to apply the checked-in column grants. Runtime startup refuses the owner, wrong identity, role memberships, schema creation or assignment-write privileges. Device identity/revocation transitions also have database invariants. There is no automatic production migration.

Each process reads its own owner-only JSON file through `SYN443_ENROLLMENT_CONFIG`: `listen`, `origin`, `issuer`, `audience`, `clientId`, `database`, `encryptionKey` (base64, 32 random bytes), `roots` (key ID to base64 DER P-256 public key), and API `certificate`/`certificateKey`. Fixture-only `fixtureHttp` defaults false. The worker/owner CLI additionally use `SYN443_ENROLLMENT_GRANTS`, a private JSON array of grants; the worker also uses `SYN443_POLICY_SIGNING_KEY_FILE` (PKCS8 P-256) and `SYN443_POLICY_KEY_ID`. The worker key and grant file must be unreadable by the API service identity. Owner `authorize` writes the permitted assignment hash; it does not register real users by itself. Set operator-controlled absolute paths, never caller-supplied paths.

This initial schema targets a fresh pilot database; upgrades from an existing production identity schema, key rotation, retention/maintenance under prolonged load, full RBAC/admin sessions, offline logout reconciliation and invitation enrollment are pending. Do not deploy the pilot publicly as a complete service.

## Reproducible evidence

The locked `contracts/v1/enrollment-openapi.json` specifies the four endpoints and bounds. Go tests validate normative request/session shapes, duplicate/case-variant rejection, OIDC/DPoP crypto, admission budgets and transport/file limits. `tools/test_enrollment.sh` creates only its own digest-pinned temporary PostgreSQL fixture and runtime roles. Race tests exercise quota contention, encrypted persistence across new store objects, refresh/replay/idempotency, revoke, grant denial, publisher isolation and renewal. It deletes only its own container/volume. The API/store/publisher coverage gate is 80%; Android protocol/boot/state classes require 90% line coverage and thirteen actual non-skipped JVM test methods. Actual database daemon restart, end-to-end Android enrollment and physical configuration activation remain distinct checks.

Toolchains now require patched Go 1.27.3 for the control plane and Go 1.26.10 for the Android native engine. The CI vulnerability gate detected [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) in the earlier runtime; it remains mandatory. Native build admission and AAR metadata checks enforce the exact engine-lock toolchain. A cached older AAR is usable only for compile diagnostics, never accepted as the patched release.
